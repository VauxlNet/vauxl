# ADR-008: Server Architecture — Evolving Modular Monolith (Cargo Workspace)

**Status:** Accepted
**Date:** 2026-01-01

## Context

The server must serve many functions (Matrix CS API, federation, media,
identity, push, admin) while the team is small. Premature microservice
decomposition adds operational overhead that slows iteration.

## Decision

Structure the server as a Cargo workspace with eight crate members. The
workspace compiles to a single binary (the "modular monolith"). If and when a
component needs independent scaling or deployment, it can be extracted to a
separate service without changing its public API — the crate boundary serves
as the future service boundary.

## Consequences

- Positive: single binary simplifies development, testing, and deployment.
- Positive: crate boundaries enforce module isolation without network overhead.
- Positive: extraction path is clear — crate API becomes gRPC/REST API.
- Negative: all components share the same process — a panic in any crate
  crashes the server (mitigated: `catch_unwind` on request boundaries).
- Negative: compile times increase with every new crate.

## Alternatives Considered

- **Full monolith (single crate)**: no isolation, risks spaghetti.
- **Microservices from day one**: operational burden without proven need.
