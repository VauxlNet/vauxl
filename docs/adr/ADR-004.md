# ADR-004: Crypto Backend — Audited Libraries for Olm/Megolm and ML-KEM

**Status:** Accepted
**Date:** 2026-01-01

## Context

Vauxl requires both standard Matrix E2EE (Olm/Megolm) and post-quantum key
establishment via the VSX extension layer. The crypto backend must use vetted,
audited libraries rather than bespoke cryptographic implementations.

## Decision

Use `vodozemac` for the Olm/Megolm baseline and `pqcrypto-kyber` (wrapping
the liboqs/Kyber implementation) for ML-KEM (FIPS 203) key encapsulation.
The X-Wing hybrid KEM composition (X25519 + Kyber-1024) is assembled at the
application layer using `x25519-dalek` and `pqcrypto-kyber`, per the
construction defined in the Matrix spec's room version 11 extension points.

All crypto primitives are gated behind the `vauxl-crypto` crate's public API.
No other crate may import raw crypto libraries directly.

## Consequences

- Positive: audited implementations for all cryptographic primitives.
- Positive: ML-KEM is a FIPS-standardised post-quantum algorithm.
- Positive: single crate owns all crypto logic — audit boundary is clear.
- Negative: `pqcrypto-kyber` wraps C code via FFI (mitigated by audit and
  sandboxing).
- Negative: X-Wing composition is not yet standardised at the Matrix spec
  level — requires VSX extension spec.

## Alternatives Considered

- **Pure Rust Kyber implementation**: available but less vetted than liboqs.
- **OpenSSL**: rejected per workspace lint policy (`deny.toml` bans openssl).
